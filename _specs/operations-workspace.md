# Operations workspace and service changes

## Outcome and scope

Staff can inspect the pilot corridor, review a proposed delay/cancellation/platform change/early ending, explicitly confirm it and see the committed result. Two editors cannot silently replace one another's work. Follow [this handoff](../docs/app-spec-plan.md#3-operations-workspace-and-changes--copy-this-prompt), [app foundation](app-foundation.md), [staff features](../docs/Features/03-railway-operations-web-features.md) and [backend change rules](operations-changes.md). User confirmed Operations implementation is light only. The 18 October Figma design pass includes both Light and Dark counterparts; see [Ops hi-fi](ops-hi-fi.md). Keep the existing Figma workflow and Keycloak session integration.

## Current source and decisions

- `apps/ops-web/src/App.tsx` and `auth.ts` are the working account/session starter, not a corridor application. `RailEndpoints.cs`, `Running/RunningEndpoints.cs` and `Changes/PublicChangesEndpoint.cs` provide dated timetables, running and confirmed state. Compose these bounded reads with a small concurrency limit; no corridor projection or map dashboard is initially needed.
- `services/api/Modules/Operations/Changes/StaffChangeEndpoints.cs` maps POST `/api/operations/journeys/{id}/changes/preview`, POST `.../changes` and protected GET `.../audit`. Its `ChangeRequest` carries either a draft or `withdrawChangeId`, optional `incidentId`, and `previewedVersion` at confirmation. Reuse its exact DTOs; no speculative fields/free-text reason editor.
- `Access/PilotRoles.cs` gives Controller `changes.publish`; StationStaff has `changes.publish_platform` for granted stations. Auditor has read permissions; SysAdmin has no operational write authority. Evaluate `/api/me` permissions/scopes, not role names or Keycloak claims. All server checks remain authoritative, including expired grants/revocation.
- Reports/incidents/auditor screens belong to [operations reports](operations-reports.md); health/simulation to [demo controls](operations-demo-controls.md). The composer may select an existing open incident only with `incidents.manage`. A standalone change remains valid; incident management is not a prerequisite for all changes.

## Screens and behaviour

1. **Corridor overview:** service date, train, last-known station, delay, operational status and observation age. Load today's dated journeys and the prior service dates needed for overnight trains; do not claim Kandy is seeded. Filter station-scoped work appropriately. Poll visible data every 15 seconds with ETags, bound fan-out and refresh on resume/reconnect. Keep schedule, confirmed state and observation failures separate. Empty success, initial loading, partial rows, whole connection loss and unknown evidence have distinct treatments.
2. **Journey workspace:** ordered stop occurrences, scheduled/expected times and current confirmed changes. A Controller chooses DELAY/CANCEL/PLATFORM/EARLY_END. StationStaff sees only platform actions at a granted station; do not permit an incident link without its separate permission. Read-only users never see a working composer. Direct URLs and a permission lost while editing show an access state without leaking protected content.
3. **Review:** call preview and render before/after, affected stops/screens/briefing, early endpoint and unserved later stops, with catering eligibility and counts exactly as supplied. Unknown counts stay unknown; publication never means provider delivery is complete. Preview has no side effects. Store the exact reviewed request and whole-journey `previewedVersion`; any change to draft, target or incident invalidates review and disables confirmation.
4. **Confirm/withdraw:** explicit action with an in-flight guard. Success follows the confirmed server response, then refreshes affected reads. Withdrawal previews a specific active change and uses the same review/confirm path; it does not restore a replaced older override or revive cancelled food orders.
5. **Conflict/uncertainty:** `409 STALE_PREVIEW` keeps useful input, invalidates review and reloads current state; require another preview and explicit confirmation. Do not retry with a newer version. If the write response is lost, say **Outcome not confirmed**, read current confirmed state and show what is now effective. Never announce that this user's action succeeded solely because a similar change exists. If still uncertain, let the user compare current state and create a fresh reviewed action; no automatic replay, offline write queue or second submission on timeout.

The composer cannot promise an individual public confirmer: the user selected **Staff-confirmed change · [time]** for public screens. Protected audit remains separate; Controller does not automatically receive `audit.read`. Short public wording comes from supported change kinds, not an invented incident reason.
