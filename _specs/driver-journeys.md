# Driver journeys and reports

## Outcome and settled scope

An authenticated assigned driver can read a dated briefing, reopen its last downloaded copy honestly offline, manually send a short stopped-use report and distinguish server receipt from explicit Control acknowledgement. Follow [handoff 5](../docs/app-spec-plan.md#5-driver-journeys-and-reports--copy-this-prompt), [driver scope](../docs/Features/02-driver-operator-app-features.md), [identity](identity-and-permissions.md), [report backend](driver-reports.md), [foundation](app-foundation.md) and [driver Figma work](driver-hi-fi.md). This is the separate `apps/driver_app/`, with the documented light default, tablet priority, readable phone companion and large targets.

No automatic offline sending: keep drafts and provide explicit manual retry. Only `TRAIN_FAULT`, `SIGNAL_DELAY`, `OBSTRUCTION`, `CANNOT_CONTINUE` are accepted; no free-text note, chat or photo. Urgent issues point to established radio/emergency procedures and never wait in a queue. The app gives no speed, signal or movement authority.

## Offline access — user confirmed

After a previous successful sign-in and briefing download on this device, allow the same driver's saved briefing to reopen **read-only** when an offline restart cannot refresh an expired access token. Show its download/check time and an explicit saved/old-data label. Expired access credentials do not grant any server authority or enable report submission. A transport failure alone must not erase the locally recognised owner or saved briefing.

Sunil's simulated advice (`cnv_99871d35d48347c79edc`) favours read-only access until logout/account switch/online rejection. Only that usability advice is considered: his examples of speed restrictions/formation information do not expand this pilot's scope.

Cache only an account/journey-specific briefing in app-private storage with an owner marker in secure storage, download/check time and schema version; no mobile database or general cache framework. First-ever offline start has no briefing. Logout/account switch clears the prior owner's content/drafts and invalidates in-flight responses. A definitive online session/access rejection, disabled account or removed assignment immediately locks and clears affected saved content; do not misclassify a connection failure as such a rejection. On reconnect refresh credentials and validate account/assignment before enabling server actions or replacing the briefing. An offline snapshot cannot know a revocation that occurred while disconnected. Keep saved schedule/confirmed changes explicitly historical; current position/ETA age into UNKNOWN, never remain live from download time.

## Flow and report recovery

1. Login → assigned dated journeys/empty state → briefing → change detail; Updates and Reports use the existing Figma navigation. Show timetable, current/ageing evidence and confirmed issuer/time separately. Poll visible mobile data every 30 seconds; refresh on resume/reconnect without overlap, and age through 304/background time using server correction.
2. Select a reason while stopped and review/send. Persist one UUID `clientReportId` plus account/journey/reason before sending. Initial unsent draft says **Not sent — Control has not been told**. If a network response is lost, say **Receipt not confirmed** instead of asserting Control definitely never received it.
3. POST `/api/driver/journeys/{id}/reports` with `clientReportId`/`reasonCode`. A 201 or identical-retry 200 records server receipt as `SENT_AWAITING_CONTROL`. On uncertainty, GET the same own-report list with `clientReportId`, or manually retry unchanged with the same key after reconciling; retain the key through restart. An empty lookup alone is not proof an in-flight original can no longer commit. Never auto-send a queued draft.
4. Read own reports/status until `ACKNOWLEDGED`; only server `acknowledgedByName`/`acknowledgedAt` produces **Acknowledged by … at …**. No local toggle. A 409 `CLIENT_REPORT_ID_IN_USE` needs reconciliation/correction, never silent new-key replay. 401/403 stop protected polling/actions, preserve only content allowed by the settled offline policy, and explain sign-in/access loss.
