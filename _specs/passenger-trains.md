# Passenger trains

## Why and done

A guest can immediately check Gampaha → Colombo Fort, change the route, compare the next two or three trains and inspect a train without signing in. The app distinguishes timetable, simulated evidence, confirmed changes and predictions, and remains useful offline without showing an old ETA as current.

## Flow and server addition

1. Open public Trains, initially GPH → FOT; select valid origin/destination by station ID. Separate scheduled origin arrival/departure from estimated times, boarding platform, delay and evidence age. Use departure when a starting station has no arrival. Route changes cancel/ignore superseded responses.
2. Show route-relevant cancellation, early ending and boarding-platform notices prominently, including old/new platform where available. A cancelled or destination-unserved train is never a recommendation. Retain an informative notice even when it leaves the eligible train list. Later-stop changes stay in detail.
3. Detail uses dated journey and stop-occurrence IDs, ordered stops, last-known station and a static route diagram. Name the early endpoint and mark later stops unserved. A moving marker is optional polish after the required checks, and must disappear at UNKNOWN; a static diagram satisfies this spec.

Proposed anonymous `GET /api/live-next-trains?originId=...&destinationId=...`: use the existing Rail matching/time/calculation rules plus `IConfirmedChangeReader`. Return up to three eligible route matches, origin/destination stop IDs, scheduled and nullable expected times, planned/effective platforms, evidence/threshold data and separate relevant confirmed notices. Use the existing bounded service-date range (previous two through next date), occurrence-aware matching and deterministic ordering. Inspect the entire bounded candidate set before taking three. Include a delayed train whose origin departure has not occurred even after its scheduled time; remove it only when observed progress proves departure or the effective service no longer serves the route. An overdue train without usable evidence remains explicitly uncertain, never claimed catchable/on-time or ranked as an estimated-arrival recommendation. Return confirmed cancellation/early-end notices separately from eligible choices. Prefer current/ageing expected departure for display ordering, schedule as a labelled fallback; highlight earliest destination arrival only among CURRENT, served, non-cancelled estimates. If evidence does not support a comparison, show none.

Return the server clock header on 200/304 and ETags for the represented state, including time-driven threshold/prediction changes. Reuse current response fields/provenance instead of inventing a second ETA model. Same invalid/unknown station and empty-result semantics as scheduled reads. No new database tables. Keep confirmed notices and running data internally consistent within the read; journey version accompanies confirmed state. Driver/board aggregation remains in its owning spec.

## Freshness, persistence and failures

- Poll visible mobile content every 30 seconds, refresh on resume/reconnect and after relevant writes, without overlapping requests. Keep data/ETag per route/journey; 304 retains the data and observation timestamp. Correct device time from `X-SmartRail-Server-Time`; continuously age from `observedAt`, not response receipt. Use [shared vectors](../tests/SmartRail.Api.Tests/Rail/freshness-vectors.json).
- AGEING starts at 180 seconds; at 240/no evidence remove ETA/current position and say unknown. Separately confirmed platforms remain with confirmation time while connected. A missing running read must not erase an independently successful timetable/change read; label the failed part. Empty success is not failure.
- Persist a small public timetable snapshot with service dates, station names, stop IDs, source and download time, plus separately dated last-known confirmed notices. On offline reload show **Saved timetable / offline**, age and scheduled times only; never present a cached platform override or prediction as current. Historical confirmed notices may be shown only explicitly as saved/unverified. No-cache cold start explains unavailable data and offers retry. Reconnect and Colombo date rollover refresh the required service dates.
- Public cache contains no token, account ID, saved subscription or pickup code. Sign-out does not erase public timetable; personal cache ownership is separate. Keycloak failure cannot block these reads.
- Localise home/list/detail fixed wording in Sinhala/Tamil/English using foundation fonts and message keys; allow long wrapping and 200% text. Mark reader review pending until real people review. Keep schedule provenance and **SmartRail simulation** visibly distinct.
