# Operations service changes

## Why

Staff need to review a service change before confirming it, and passengers need one consistent result. A second controller must never silently overwrite a decision made after their preview.

## Done when

An authorised staff member can preview, publish and withdraw a delay, cancellation, platform change or early ending for a dated journey. Public reads expose the confirmed state; an auditor can see who acted and when. Publishing from an old preview returns 409 with the latest journey version, leaving the confirmed state unchanged. Ending a journey early keeps its final stop and earlier stops valid and marks later stops unserved and ineligible for food collection.

## Decisions

- Follow the [backend decision](../docs/architecture/backend-decision.md#code-boundaries): feature slices in `services/api/Modules/Operations/`, plain C# rules, the existing EF context, and `Program.cs` wiring only. Use small named interfaces for Rail journey/stop reads, Access permission/audit work and Catering outbox writes; Operations must not query their EF sets. Add the required module-boundary check when Operations becomes the second module.
- Use the [Operations ERD](../docs/architecture/erd/02-operations.mmd) and [data-model rules](../docs/architecture/data-model.md#tables-and-rules-not-fully-visible-in-the-diagrams). Initialise one journey version row at **0** for every existing and newly seeded journey, without resetting it on reseed. Changes are append-only `PUBLISH`/`WITHDRAW` rows, uniquely keyed by `(journey_id, journey_version)`; never edit the timetable or delete history. Actor IDs and UTC confirmation times come from the server.
- Validate only the fields relevant to the kind: `DELAY` has non-negative integer `delay_minutes`; `CANCEL` has no type-specific fields; `PLATFORM` has a nonblank `new_platform` and `target_stop_id`; `EARLY_END` has `final_stop_id`. Reject unrelated fields. Both stop IDs mean pattern-stop **occurrences** belonging to this journey's pattern, not station IDs. An early endpoint must be an intermediate stop with a scheduled arrival. Unknown journeys/changes return 404; malformed or inapplicable drafts return 400.
- Fold history in journey-version order. A newer publish replaces the active override of the same kind, independently per stop for platform changes. Withdrawal references the currently active publish via `supersedes_change_id`; withdrawing an already withdrawn or replaced publish returns 400 after the version check. Withdrawal clears that override without reviving an older one, preserves other kinds, and returns that field to its underlying Rail state. For example, withdrawing a 25-minute delay that replaced a 10-minute delay removes the confirmed delay; a current observed delay can still remain. This adopts Dilani's Operations Controller advice from conversation `cnv_3b121e7b0ec34d3cac16` to avoid restoring obsolete restrictions.
- Preview returns the validated draft, `previewedVersion`, before/after confirmed state, affected stop occurrences and screen/briefing impacts. For early ending, name the new final station and list unserved later stops. Show food-order impact as expected eligibility changes, with counts only when Catering can supply them; unavailable counts are unknown, not zero. Preview creates no change, version increment or provider message and makes no Grilled call. Read version and history consistently; publish recomputes validation and impact rather than trusting client-supplied impact data.
- Use [SmartRail permissions](../docs/06-scope-decision.md#who-can-do-what) and the [identity boundary](../docs/architecture/identity-and-local-development.md#identity-boundary). Controllers publish/withdraw network-wide; StationStaff can preview/publish/withdraw platform changes only at their granted station. Recheck local account status, permission, grant expiry and scope on every staff request. Guests get 401; authenticated unauthorised users, including SysAdmin and Auditor attempting writes, get 403. Denied staff writes are audited without request bodies, tokens or secrets.
- Publish and withdraw require the same draft/action and whole-journey version reviewed in preview. In **one PostgreSQL transaction**, conditionally advance `v` to `v+1`, append the change and successful Access audit row, and enqueue any required Catering message. A zero-row version update returns a Problem response with code `STALE_PREVIEW`, `previewedVersion` and `latestVersion`; no change/outbox/version advance survives. This applies even when another person changed an unrelated kind or stop. An authorised rejected attempt can have a separate failed audit entry. A fresh preview and explicit confirmation are required; never automatically retry the write with a newer version. This is separate from food-cutoff 409 and observation freshness.
- Cancellation overrides service availability. Early ending keeps stops through the final occurrence inclusive; later stops have no operational arrival estimate or pickup eligibility. Independent platform confirmations survive stale observations. Recompute availability on withdrawal while retaining other active changes. Catering messages carry the resulting journey version and full eligibility snapshot (`order_closed`, `blocked_pickup_stop_ids`) for cancellation, early ending and their withdrawals; delay messages follow the Catering ETA contract. Publishing succeeds while Grilled is down because the outbox is durable; delivery and existing-order cancellation are eventual, not claimed at commit time.

## Proposed API

| Route | Result |
| --- | --- |
| `POST /api/operations/journeys/{id}/changes/preview` | Authorised preview of a publish draft or withdrawal referencing a change ID. |
| `POST /api/operations/journeys/{id}/changes` | Confirm that action with `previewedVersion`; return change ID, new version and confirmed state. |
| `GET /api/journeys/{id}/changes` | Anonymous confirmed state, journey version, active change IDs/times and served/unserved stop occurrences; no staff identity or audit data. Support ETag/304. |
| `GET /api/operations/journeys/{id}/audit` | Audit-read permission required; chronological, bounded history including actor, action, target, outcome, UTC time and correlation ID. |

## What exists now

- [Public timetable](public-timetable.md) supplies dated journeys and ordered stop occurrences in `Modules/Rail/Timetable/`, Rail EF mappings and fictional seeds. `Infrastructure/SmartRailDbContext.cs` currently maps only `network` data; `RailEndpoints.cs` provides three anonymous scheduled-only reads.
- `tests/SmartRail.Api.Tests/Rail/TimetableApi.cs` already supports disposable PostgreSQL endpoint checks using `SMARTRAIL_TEST_POSTGRES`.
- Operations, Access account/permission/audit support, Catering outbox and live ETA/freshness are absent. The local stack runs Keycloak, but `Program.cs` does not validate its tokens. [Identity and permissions](identity-and-permissions.md) and [simulated running](simulated-running.md) plan these dependencies; Grilled currently serves only health.

## Boundaries

This is the backend Operations change flow. Staff/client screens, observation ingestion and ETA calculation rules, driver reports/incidents, full identity setup, food placement, Grilled outbox delivery/webhooks and cancellation of existing orders belong to their own features. Keep the current timetable routes labelled scheduled-only; consumers use the confirmed-state contract when building operational views. Do not claim passenger/station/driver propagation or provider cancellation until those integrations are demonstrated. No SSE, SignalR, offline staff writes or safety-critical train-control instructions.
