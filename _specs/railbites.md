# RailBites ordering and reliable delivery

## Why

Passengers need an order that follows their train, including a clear cancellation when it cannot reach the collection stop. This proves the pilot's external-service boundary survives timeouts and outages without duplicating orders or losing confirmed changes.

## Done when

Through APIs, a signed-in passenger can browse food, place one retry-safe order, read its pickup code and provider status, and cancel before the provider cutoff. Authenticated kiosk calls can mark it Ready, Collected or No-show. A confirmed delay updates pickup time; cancellation or early ending cancels affected open orders with a reason. Stopping either service and restarting it eventually delivers pending changes and callbacks once in effect, while public train information remains available.

## Decisions and boundaries

- **User-confirmed scope:** service integration first: ordering APIs, train changes, retries and callbacks. Include kiosk action APIs and local failure controls, but no passenger food tab, kiosk page or Operations health UI. This covers Epic 5 and the catering part of Epic 6's reliable updates/health; it does not claim propagation to all client apps.
- Follow the [backend decision](../docs/architecture/backend-decision.md), [food rules and D7-D12](../docs/06-scope-decision.md#food-ordering-rules), [data-model rules](../docs/architecture/data-model.md) and [two catering ERDs](../docs/architecture/erd/04-smartrail-catering.mmd). Keep one SmartRail context and feature slices in `Modules/Catering/`; RailBites remains a separate Node/TypeScript service with SQLite. Cross-module reads use named interfaces. No broker, separate worker deployment or shared C#/TypeScript models.
- RailBites owns collection points, menu, stock, prices in minor LKR, cutoff, pickup codes and order status. Seed Polgahawela Junction and Peradeniya Junction against the actual SmartRail station IDs. Keep seeds repeatable without resetting orders or stock on restart. Pass no passenger names, contact details or Keycloak tokens to RailBites. Pay at collection; no online payment, refunds, order editing, ratings or pushed stock updates.
- SmartRail uses Access's `orders.manage` and checks local account status plus ownership on every personal read/write. Never return another account's order or pickup code. RailBites service routes require a separate configured service credential; kiosk actions require a distinct credential scoped to their collection point. Missing credentials fail closed. Credentials come from secrets/environment, never clients or Git.
- Offer only served stop occurrences still ahead of the train, on a journey whose Colombo service date is today, with a usable current/ageing ETA. Unknown status blocks new orders, including retries that would create one; it does not cancel existing orders. Validate collection point/station/stop membership on the server. At submit RailBites atomically checks active items, positive quantities, stock, journey eligibility and `now < ETA - cutoff`; equality is closed. Default cutoff is 30 minutes and is provider-owned; changing it to 45 requires no SmartRail change. Menu may be cached for 60 seconds; cutoff is never cached. Return stable reason codes for stock, cutoff, unknown train and unserved stop.
- Use `(account_id, client_request_key)` for SmartRail idempotency and generated `order_links.id` for provider idempotency. Persist the original request before calling the provider. Concurrent identical submissions return the same link/order; reusing a key for different items, journey or pickup returns 409. Retain a canonical request digest after clearing temporary request JSON on confirmation/final rejection. Provider lookup/repeat returns an existing order's **current** status before applying new-order cutoff/stock checks. Stock deduction, order/items and initial callback enqueue commit together in SQLite. A timeout is pending/unknown, never proof of rejection.
- Before any timed-out placement retry, recompute eligibility. If no longer eligible, perform authenticated lookup/reconciliation only, not a new placement. Keep an ambiguous request pending until its outcome is known; do not present it as safely rejected while the original may still commit. A late accepted order is corrected by the durable train-change event. Preserve the same link ID throughout; never mint another ID to resolve uncertainty.
- Order states are `ACCEPTED`, `READY`, `COLLECTED`, `NO_SHOW`, `CANCELLED`; placement/rejection uncertainty belongs to the SmartRail link, not a fabricated provider order. Allow ACCEPTED -> READY -> COLLECTED, and open orders -> CANCELLED or NO_SHOW under their respective rules. Collection requires the matching code; No-show requires a fresh authenticated SmartRail read showing the train has passed that pickup occurrence, not a guess from scheduled time or a kiosk-supplied boolean. Passenger cancellation requires a fresh eligibility/ETA check and provider cutoff approval. Repeat actions are harmless; conflicting terminal actions return 409. Store a cancellation reason and increment a per-order sequence on every externally visible change, including ETA changes.
- **Operational interpretation:** train cancellation/early ending cancels ACCEPTED/READY orders at newly unserved stops, preserving COLLECTED/NO_SHOW/CANCELLED history. Withdrawal reopens new-order eligibility without reviving cancelled orders. Dilani, Operations Controller, supported this rule in conversation `cnv_5ef5b521ad9848128654`; this is expert advice, not an additional user scope decision. Restore reserved stock once for cancelled orders; never on callback retries or terminal collection/no-show.

## Integration contract to implement

Write `services/railbites/openapi.yaml` before implementing order writes. Keep signed JSON examples as test fixtures, not shared runtime classes. Exact field/header names and error schemas belong in that contract; include these operations:

| Boundary | Operations |
| --- | --- |
| Passenger -> SmartRail | Browse journey collection options/menu; create, list and read own order links; cancel own order. Pending placement returns 202 and a stable link to poll. |
| SmartRail -> RailBites | Collection points/menu; idempotent placement; lookup by SmartRail link ID; cancellation; train-change delivery. |
| Kiosk -> RailBites | List its collection point's orders and perform Ready/Collected/No-show actions. |
| RailBites -> SmartRail | Signed status/ETA/reason callback carrying event ID, link ID, provider reference and status sequence. |

- Placement carries dated journey/train identity, stop occurrence/station/collection point, scheduled arrival, current ETA with evidence time, journey version/full eligibility snapshot and items. SmartRail supplies these from Rail/Operations, not from passenger input. RailBites serializes new placement and journey-state changes using SQLite `BEGIN IMMEDIATE`; apply newer journey versions only and reject inconsistent eligibility at the same version. A placement must not bypass a newer restriction already received by the provider.
- Extend the existing transactional `TrainChangeMessage`/outbox to include pickup-stop scheduled times and nullable effective ETAs with calculation/evidence times. Calculate them through Rail's existing rules using the **post-change** state before commit; enqueue the resulting full snapshot atomically with change and audit. Every food event carries full eligibility and the pickup-time snapshot so a newer version supersedes older events, including delay withdrawal. Platform-only changes need no event; journey versions need not be consecutive at RailBites. Pending rows with the older payload format must be handled explicitly during migration/setup, never silently marked delivered.
- Delivery retries keep event ID and payload stable. RailBites atomically records the received event, advances its journey snapshot, updates affected open orders and queues callbacks. Duplicate/older events cannot reverse newer state. A null ETA is unknown, never replaced with schedule or made fresh by retry; cancellation eligibility still applies without an ETA. Existing order views expose the provider's last reported pickup time with its evidence time. This pilot sends confirmed-change updates, not every simulator tick; placement/cancellation supplies fresh evidence for cutoff decisions.
- Both outboxes persist attempt count/next attempt, retry with capped increasing delays after timeouts/503, and acknowledge only after the receiver commits. Keep transient failures retryable across restarts; surface permanent contract/auth failures for correction without dropping messages. Use hosted loops inside the existing services. A crash after receiver commit but before acknowledgement safely redelivers.
- Sign callbacks with HMAC-SHA256 over a documented timestamp delimiter and exact raw UTF-8 body; constant-time comparison, five-minute timestamp tolerance and bounded bodies. Sign each retry with a fresh timestamp while preserving event ID/body. Authenticate before duplicate handling. Receipt and conditional update commit together in PostgreSQL; only a greater sequence updates the link. Valid duplicates/older sequences get a successful no-op acknowledgement so delivery can finish, while invalid signatures/timestamps are rejected and counted. A duplicate ID with different content is a conflict. Never expose pickup codes, signatures, secrets or payloads in logs.

## What exists now

- [Local foundation](local-foundation.md) runs both services in Aspire. RailBites has a SQLite store, an OpenAPI contract and authenticated collection-point/menu reads (T1), and the provider order, cancellation and kiosk APIs with a durable callback outbox (T2). SmartRail has order links, a provider client, public browse reads, protected own-order endpoints and a pending-placement retry loop (T3), and a durable outbox dispatcher that delivers confirmed train changes with post-change pickup times (T4); RailBites now delivers signed status callbacks from its durable SQLite outbox; SmartRail validates the raw-body signature and commits sequenced order updates with durable receipts (T5).
- [Identity](identity-and-permissions.md), [simulated running](simulated-running.md) and [Operations changes](operations-changes.md) supply account checks, stop-level predictions and confirmed state. Reuse their existing interfaces/calculators and disposable PostgreSQL test setup.
- `Modules/Catering/ICateringOutbox.cs` and `Outbox/OutboxMessage.cs` stage versioned eligibility and post-change pickup times in the Operations transaction. `OutboxDispatcher` delivers them; `Orders/` owns passenger links and reconciliation; `Callbacks/` owns signed receipts and status updates. Architecture documents describe the target; their old implementation-status paragraphs are not evidence of current code.

## Feature acceptance checks

1. Browse, place, retry, mark Ready, collect by code and read Collected through SmartRail. Attempt another passenger's read/cancel and another kiosk's action; all are denied without leaking the code.
2. Delay a train and observe the revised pickup ETA/cutoff; block ordering at unknown freshness. Exercise free cancellation before cutoff, rejection at/after it and No-show only after confirmed departure.
3. Order beyond an early endpoint, stop RailBites, publish the change and verify train reads still work. Restart RailBites and observe one reasoned cancellation. Withdraw and redeliver the old event: new eligible orders are allowed, cancelled ones stay cancelled.
4. Lose placement responses on both sides of the provider commit, then publish an early ending before retry. Prove no duplicate/late surviving ineligible order, and no false final rejection while the earlier outcome is unknown.
5. Stop SmartRail during kiosk status delivery, restart it, and prove signed callback retries converge without status regression or duplicated stock effects. Restart both services and verify orders, receipts and pending deliveries persist.
