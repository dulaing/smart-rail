# Simulated running: observations, ETA and unknown

## Why

Passengers and staff need a usable estimate without mistaking the demonstration for a real railway feed. When observations stop, an old position must stop looking current.

## Done when

A guest can inspect a dated journey's scheduled stops, simulated position, delay and estimated arrivals. Pausing observations makes the response ageing at three minutes and position/ETA unknown at four; a fresh observation restores them. Scheduled times and planned platforms remain available throughout, with honest source labels.

## What exists now

- [Public timetable](public-timetable.md) is implemented under `services/api/Modules/Rail/`: dated journeys, ordered stop occurrences, Colombo time conversion, fictional seeds and three anonymous reads. `NextTrainFinder.cs` selects trains by scheduled departure.
- `services/api/Infrastructure/` supplies one EF context, explicit migrate-and-seed, migrations and `ETagResults.cs`, which hashes the response body. `Program.cs` already registers `TimeProvider` for controllable time.
- The Rail source currently has no observation storage, running-status read, ETA rules or simulator. Reuse `tests/SmartRail.Api.Tests/`; database checks use `SMARTRAIL_TEST_POSTGRES`.

## Decisions

- Follow the [backend boundaries and update contract](../docs/architecture/backend-decision.md): keep this slice under `Modules/Rail/Running/`, use the existing context, and keep calculation rules in plain C#. `Program.cs` only wires services/routes. Polling with ETags is sufficient.
- Use [the observation model](../docs/architecture/data-model.md#tables-and-rules-not-fully-visible-in-the-diagrams) and [ERD](../docs/architecture/erd/01-timetable-running.mmd). Store `live.observations` with journey ID, unique `source_event_id`, adjacent `from_stop_id`/`to_stop_id`, integer `progress_permille` (0–1000), `reported_delay_seconds`, `observed_at` and server-assigned `received_at`. Both stops must belong to that journey's pattern; adjacent means neighbouring ordered occurrences, not consecutive numeric sequence values. Keep UTC instants and original observation time. Do not store ETA or freshness rows.
- Proposed ingestion: `POST /internal/rail/observations`, protected by a configured service key from user-secrets/environment; fail closed when absent. Anonymous writes are never allowed. Return 201 for a new event, 200 for an identical retry, 409 for reuse of its key with different input, 404 for an unknown journey, and 400 for malformed timestamps, future observations, invalid segments/progress or negative delay. Enforce uniqueness in PostgreSQL so concurrent retries are safe. Older valid events remain history; select current evidence by greatest `observed_at`, with an ordinal event-ID tie-breaker, never `received_at`.
- Apply [scope rules D3–D6](../docs/06-scope-decision.md#how-the-system-will-work). Age is `now - observed_at`: **CURRENT** below 180 seconds, **AGEING** from 180 to below 240, **UNKNOWN** at 240 or with no observation. Receipt, polling and retries cannot reset age. Unknown means `currentPosition`, current delay and estimated arrivals/departures are null; retain the last observation separately as historical evidence. Never infer “on time” from the timetable alone.
- While current or ageing, delay in seconds is `max(0, reported delay, confirmed delay if available, now minus scheduled arrival at the next unpassed stop)`. ETA is scheduled arrival plus this delay; estimated departure is no earlier than scheduled departure. Apply the same delay to later stops, without a recovery or travel-time model. Progress below 1000 means the next stop is `to_stop_id`; 1000 means at that stop, with the following occurrence next. Do not return future arrival predictions for already reached stops. Dilani (operations, conversation `cnv_3d0fc8bead3a4c3b83e2`) supported clamping an overdue next-stop ETA to server time and carrying that delay forward; expose delay alongside ETA so it is not presented as guaranteed imminent arrival.
- Proposed guest read: `GET /api/journeys/{journeyId}/running`; malformed ID returns 400, missing journey 404. Return ordered stop IDs/station IDs, scheduled instants and planned platforms, timetable provenance, running label **SmartRail simulation**, latest observation timestamps/last-known station, freshness, current segment/progress, delay and nullable stop estimates. A published timetable still has simulated running. Reuse Colombo/day-offset rules, including arrival-before-midnight/departure-after-midnight dwell. This endpoint adds detail; existing timetable reads keep their scheduled matching and ordering.
- Supply thresholds (180/240 seconds) and `X-SmartRail-Server-Time` on every 200/304. Clients use server/device clock correction and continue ageing cached evidence between polls. Keep continuously changing age/server time out of the body and ETag. Hash the represented state: new evidence, threshold crossings or changed predictions require 200/new ETag, even without a database write; unchanged represented state permits 304. An overdue prediction that changes with time legitimately changes the ETag.
- Simulator: an opt-in hosted worker in the API emits every 30 seconds through the same validated ingestion path as the protected endpoint. Use fictional seeded journeys only, deterministic timetable-based segment progress and a configurable nonnegative demo delay; never depart before schedule. During dwell, hold progress at 1000 on the inbound segment until departure; then move to the outbound segment. Start reporting at the first departure and stop after the final arrival; do not invent later positions. Provide Development-only, service-key-protected per-journey pause/resume commands and a short local run example. Pause stops observations, not server time; resume emits newly observed evidence without replaying missed ticks or deleting history. No simulator console UI is needed.

## Boundaries

This is a backend slice. Passenger/station/operations UI, maps, client polling/cache implementations, Dart/TypeScript runners for the shared vectors, public route ranking by ETA, real feeds/GPS, SSE, food gating and staff change workflows belong to later features. The response's unknown state is their future input; no “unknown” event goes to RailBites here.

Confirmed delays, cancellations, platform changes and early endings belong to Operations; do not add their tables in this slice. Their later integration must supply effective changes through an explicit interface: confirmed cancellation/early ending takes precedence, and independently confirmed platforms retain their own timestamps when observations become unknown. That integration check depends on the Operations feature and is not claimed complete here. T1's check has passed (`dotnet test tests/SmartRail.Api.Tests`, 42 new and existing Rail rule tests). T2's check has passed against a disposable PostgreSQL 18.3 container (`SMARTRAIL_TEST_POSTGRES`), 162 of 162 tests in the project; the service key is the `Observations:ServiceKey` setting, sent as `X-SmartRail-Service-Key`. T3–T4 are planned and their checks have not been run.
