# App foundation

## Why

Give the four existing apps a consistent SmartRail identity, readable status language and usable navigation before building their train, staff and food features. Keep public information accessible when sign-in is unavailable.

## Decisions

User-confirmed in this discussion:

- Reuse the existing [SmartRail UI Figma file](https://www.figma.com/design/38B21GKxgb3wxRar06gHXP/SmartRail-UI?node-id=120-36), including its cyan accent, typography, surfaces and navigation; do not introduce another brand.
- Passenger supports both light and dark themes and retains **Home · Trains · Food · Account**, in that order. Do not combine Home and Trains.
- Operations is **light only** for this pilot.
- Public passenger/station changes use **Staff-confirmed change · [time]**; individual staff names stay in authorised staff views. Shared translations/components must preserve that boundary.
- After prior sign-in/download, Driver may reopen its own saved briefing read-only when offline token refresh is unavailable, with age shown. Logout/account switch or definitive online access rejection locks/clears it. [Driver journeys](driver-journeys.md) owns this cache behaviour; it grants no offline server authority.
- Planning only; this spec does not authorize implementation.

Follow [the handoff and Common context](../docs/app-spec-plan.md#common-context--every-spec-agent-must-read-this), scope [D2/D13/D15 and screen rules](../docs/06-scope-decision.md), [backend decision](../docs/architecture/backend-decision.md), and [identity contract](../docs/architecture/identity-and-local-development.md). Figma supplies visual references; the newer pilot rules govern access, freshness, language and screen behaviour. The external `C:\Projects\smartrail-system-design-v2.html` is broader architecture context, not a source of additional pilot features.

Implementation defaults, kept separate from user-confirmed choices:

- Open passenger on **Trains**, preserving all four tabs. This follows the handoff's direct public next-trains entry. Home remains a distinct destination for its existing Figma flow; its feature content belongs to passenger-trains, not this foundation.
- Passenger initially follows the device theme, with guest-accessible **System / Light / Dark** choices in Account. Remember this device preference across restart and logout; it is not personal account data.
- Driver uses the required light default, 20sp body text, at least 28sp times and 56dp targets. This foundation does not add a driver theme picker. The separate [driver hi-fi spec](driver-hi-fi.md) owns its Figma screens and dark counterparts; do not edit or duplicate its tasks.
- Station uses a fixed dark display theme, with no public theme controls. Staff apps remain English for the pilot; translation plumbing exists throughout.

Kasun's simulated passenger advice favoured retaining four tabs while opening Trains (SmartRail conversation `cnv_c25ac4af775b4834b300`). It informed the entry recommendation; it is not user testing or approval of other scope.

## What exists now

- `apps/ops-web/src/App.tsx` and `auth.ts` implement Keycloak session/account states and display effective permissions. Its CSS still contains starter styling; Station's `src/App.tsx` is the Vite starter. Neither web package currently declares a test runner.
- Figma contains `00 Foundations`, `HiFi · Foundations`, `HiFi · Components`, passenger light/dark flows and staff/display wireframes. Relevant references: [foundation documentation](https://www.figma.com/design/38B21GKxgb3wxRar06gHXP/SmartRail-UI?node-id=55-1273), [shared hi-fi tokens](https://www.figma.com/design/38B21GKxgb3wxRar06gHXP/SmartRail-UI?node-id=128-39), and [passenger navigation](https://www.figma.com/design/38B21GKxgb3wxRar06gHXP/SmartRail-UI?node-id=123-195). These were inspected in the browser; exact token values have not yet been exported or contrast-tested.
- Rail's running response already supplies observation time and freshness thresholds. `X-SmartRail-Server-Time` accompanies successful 200 and 304 running reads. Reuse [freshness-vectors.json](../tests/SmartRail.Api.Tests/Rail/freshness-vectors.json); do not create another fixture source.

## Shared foundation and contracts

- Put the small source definitions in `shared/design/tokens.json` and `status.json`. A plain Node script, `shared/design/generate.mjs`, emits CSS variables, TypeScript status data and Dart values. Commit outputs; `--check` detects drift, missing mappings and failing contrast pairs. No Style Dictionary, Figma sync, Code Connect setup or npm design-system package.
- Use one local Dart package, `packages/smartrail_core`, for generated values, theme construction, the two shared widgets and the small freshness rule. Keep existing auth implementations in their apps. Web apps import generated CSS/data and keep thin React renderers locally, avoiding a shared React dependency/package setup.
- Export actual Figma primitive/semantic colour values, type roles, spacing and radii rather than estimating them from screenshots. Reuse the hi-fi identity; document any accessibility-driven token adjustment. Preserve app-specific density. Use bundled Noto Sans, Noto Sans Sinhala and Noto Sans Tamil, with licence files and offline font loading; allow script-specific line height and wrapping.
- `StatusBadge` takes a status key and locale and renders text plus a stable icon/shape; colour alone never carries meaning. Cover on-time, delayed, cancelled, ends-at-station and platform-change presentations, and CURRENT / AGEING / UNKNOWN evidence labels. These are separate facts, not one mutually exclusive train-state enum. Never infer on-time from a schedule or a successful request. Offline/loading/errors are separate UI states.
- `FreshnessLine` receives observation time, current corrected time, server thresholds, connection state, locale and optional saved/download time. It describes current simulated evidence, ageing, unknown, or saved information honestly. Below 180 seconds is CURRENT; 180 to below 240 is AGEING; at 240 or without evidence is UNKNOWN. Clock correction comes from server time; polling/304 never resets observation age. Keep independently confirmed changes and their confirmation times outside observation freshness.
- Keep the age calculation pure and test it in Dart and TypeScript against the existing fixture. Poll scheduling, resume/304 integration, cache storage and expiry belong to consuming features. Components must not fetch, poll, calculate ETA or own a cache.
- Shared fixed status/reason keys carry English, Sinhala and Tamil wording. Use ordinary Flutter localisation resources and small TypeScript message maps for app shell strings. Do not machine-translate staff free text. Unreviewed translations stay labelled as unreviewed in this spec/evidence; do not claim language readiness without native-reader feedback.

## Shell behaviour

| App | Foundation result |
| --- | --- |
| Passenger | Figma header and four-tab navigation in both themes; Trains opens publicly. Home, Trains and Food are reachable as guests. Account hosts optional sign-in, language/theme preferences and sign-out. Only personal actions later request login. |
| Driver | Light staff sign-in shell, then the existing Figma navigation for assigned journeys/updates/reports/account. Empty content until driver-journeys is built; no sample assignments or operational actions. |
| Operations | Light staff shell, account/session controls and navigation for the permitted future workspaces. Use effective `/api/me` permissions/scopes, not Keycloak role claims. Unavailable feature content stays an honest placeholder. |
| Station | Anonymous, passive display frame: board heading/configured location, clock and fixed **SmartRail simulation** footer. Show an honest no-data state and a trilingual status sample; no invented departures, search terminal or staff controls. |

Use headings and neutral empty-content treatments for unfinished destinations; do not show hardcoded train rows, fake live status or functioning-looking publish/order/report controls. Detailed Home and Trains content, route selection and all board data belong to subsequent specs.

Preserve PKCE, web in-memory tokens, mobile secure storage, callbacks and the [documented Android issuer/CA setup](../services/README.md#passenger-and-driver-apps-flutter). Keep Keycloak credential screens external. Auth restoration/loading must not block passenger public tabs. Cancelled login and logout return to public passenger content. Driver/Operations stay protected while checking a session; expired credentials offer sign-in, disabled/unmapped accounts explain access denial and allow sign-out, and connection failures offer retry without calling them permission denials. Permission-hidden navigation does not authorize direct URLs: denied destinations show an access state and server checks remain authoritative. Do not add permission-management screens.

## Boundaries and completion

No train/food/report/change feature screens, real board reads, API additions, shared networking framework, state-management migration, offline storage, polling loop, admin UI, deployment or new logo. Do not infer implementation readiness from Figma designs or old completed backend checkboxes.

Done when all four visible shells use the shared foundation, passenger themes and original four tabs work, Operations is light only, existing guest/staff identity paths remain usable, and the task checks have recorded results. Device and native-reader availability must be rechecked when the remaining checks are run.
